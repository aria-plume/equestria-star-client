## 2. 登录及恢复

~~~text
POST /api/v1/auth/login
  → 保存accessToken与user.userId
GET /api/v1/me/active-session
  NONE → 大厅
  WAITING → 原房间，不再join
  CHARACTER_SELECTING → 选角页
  IN_GAME → 读取对应gameId的player-view
           → players中按当前userId找到局内playerId
           → 建立连接心跳
           → 读取pendingCheck及pendingReward恢复界面
~~~

房间ID、账号ID、房间成员ID、局内playerId不是同一个ID。加入房间返回的playerId是旧命名的成员记录ID，不用于connection或actions。刷新令牌没有单独路由，不能凭refreshToken字段自行拼接口。

## 3. 房间到对局初始化

1. POST /rooms创建，POST /rooms/{roomId}/join加入；GET房间详情轮询状态。
2. 普通玩家POST /ready，无请求体、不提交角色；房主不用ready。
3. 房主POST /start-character-selection，服务端进入30秒选角。
4. 每人（包括房主）POST /select-character，body为`{"selectedCharacterId":101}`，ID取GET /characters。
5. 以房间详情中的characterSelectionDeadline显示倒计时，按members的已选字段显示角色占用。
6. 服务端截止自动为未选者分配剩余角色并开局；前端不能调用旧/rooms/{roomId}/start。
7. GET房间到status=IN_GAME、currentGameId有值后，进入该局，立即接入下面的心跳。

旧房主离开不转让，允许离房阶段直接删房，其他客户端收到ROOM_NOT_FOUND回列表。正在对局不能用leave代替断开连接。对局结束后房间回WAITING，可继续下一局；新局必须重新获取gameId和playerId。

## 4. 心跳是进入游戏后的必需流程

建连：
~~~http
POST /api/v1/games/{gameId}/players/{自己的playerId}/connection?connected=true
Authorization: Bearer <accessToken>
Content-Type: application/json

{"clientInstanceId":"本次窗口连接尝试的UUID"}
~~~

保存 `data.engineState.connection.connectionId`；默认每5秒向同一路径续期：
~~~json
{"clientInstanceId":"原UUID","connectionId":"服务端返回的ID"}
~~~

无requestId或stateVersion。主动关闭改connected=false，带同样两项身份。CONNECTION_EXPIRED/CLOSED需新的clientInstanceId重新建连；正常周期心跳不生成新ID。新窗口各自有连接身份，旧窗口关闭不应误关新窗口。

默认首次45秒宽限、后续租约15秒、离线后再等10秒，由服务端处理既有兜底。登录、GET、地图轮询、普通行动均不续期；卡牌弹窗／骰子动画／等待别人的回合时也要继续心跳。按connectionPolicy返回值配置定时器，不硬编码不可变规则。

普通续期不增加stateVersion、不切回合或发奖；实际上下线会增加版本。gameStatus=RUNNING也可能pausedReason=ALL_OFFLINE；任一玩家有效重连即可解除全局暂停，后续服务端继续阶段。离线玩家可筛选players[].isConnected==0。不能匹配“对局暂停，等待重连”中文字符串判断业务。

## 5. 任务栏和货架按钮用哪些接口

| 界面内容 | 请求 | 使用内容 |
|---|---|---|
| 公共任务板三张候选 | GET /games/{gameId}/quest-offers?playerId={自己} | data.offers，questId/questCode/questName及卡面文字 |
| 已接任务、划掉完成目标 | GET /games/{gameId}/quests?playerId={自己} | data.quests、completedQuests及objectives/conditions |
| 本局公共商店货架 | GET /games/{gameId}/shop/current?playerId={自己} | data.items、inventoryScope、inventoryGameId、stateVersion、accessAllowed |
| 自己背包 | GET /games/{gameId}/items?playerId={自己} | data.totalCount、items，动作使用playerItemId |

此表路径省略共同前缀/api/v1。**不站在任务板／商店也能看牌；具体接取、刷新、买卖才校验地点。** 货架accessAllowed只表达地点资格，非全部执行资格；其他条件还看availableActions和实际错误。

每次打开面板重新GET，不使用本地固定三张卡或默认随机卡。只把返回卡牌映射到卡图；不足三张按真实数量显示。所有SHOP是同一个本局货架，cellId是玩家查询位置，不是独立商店库存身份。开局初始化抽最多三件货架及三张任务候选；打开面板不会抽牌或补货。

UI收到旧货架stateVersion，不覆盖当前较新版本。弹窗只阻塞地图输入，不中断后台心跳和状态同步。不要因为关闭弹窗清理地图、相机、棋子或整个对局状态。

## 6. 行动与任务目标

~~~json
{"requestId":"每次新操作生成的UUID","playerId":1001,"stateVersion":8,"actionType":"ACCEPT_QUEST","payload":{"questId":149}}
~~~

完整payload清单见主文档第9节。ACCEPT_QUEST不是slotNo；ABANDON_QUEST须传questId，可再传playerQuestId；提交道具用playerItemId，不用itemId。普通移动先查movable-cells，棋子按行动movement.actualTarget更新。

使用playerViewState和nextAvailableActions更新资源及按钮，任务用questUpdates或查询快照；不要本地重复发奖、扣费或推进任务。目标划线只用objectives[].completed，条件高亮用conditions[].satisfied，两者不同。049三属性目标、052实际消费、014完整停留都以服务端快照为准，不从总progress平均分配。

普通胜利在END阶段检查，特殊直接胜利例外；客户端读engineState.finalResult，支持多个winnerUserIds，不能用本地声望直接结束对局。

### 6.1 已部署：铁路与森林移动

- 铁路按钮提交USE_RAILWAY与目标车站cellId，一次只坐一站，每次1金币＋1行动值；只显示服务端返回的直接相连铁路目标。不能用普通movable-cells冒充铁路查询。
- 普通移动按出发格的森林区域判断是否需要方向骰。需要时先提交目标，取得待投骰，再物理投骰/可选重投/最终确认；准备阶段不要移动棋子。
- 最终骰点2～5到目标，1左偏、6右偏；左右相对移动方向。非法落点原地停留但扣行动值，固定6仍右偏，不能当作失败后自动重试。
- 棋子以服务端actualTarget更新；方向骰不显示属性加成或难度，不把未偏移当“判定成功”、偏移当“判定失败”。本轮不开放森林免疫伙伴。
- 界面等待期间继续心跳，恢复时从pendingCheck恢复出发格及目标；不要由前端决定真实落点、扣票价或发布到达事件。
- 字段以专项第8节为定稿，当前规则兼容已有测试局；不要采用前文草案。实际接入读取新鲜movementRulesVersion=2，本轮不代表移动UI重新验收。

## 7. 骰子、奖励和结束回合

主动骰子详见 [投骰专项](Godot_任务主动掷骰接入说明.md)：
- actions准备只传业务选择，resultType=CHECK_ROLL_PENDING时打开骰子。
- 有重投资格才POST /checks/{checkId}/reroll，只传requestId/stateVersion/authorizationRound，不传点数。
- 最终确认才POST /checks/{checkId}/roll，增加dice整数1～6；用最新版本和授权轮次。
- 成功与否、最终值、资源、奖励和目标由后端结算；超时后不能只凭本地计时认定已结算。

pendingReward是FIFO队首，不是只在回合开始才有：
- 先检查归属及canExecute/canAbandon，领取传rewardId＋cardId，放弃传rewardId＋abandon=true。
- 统一走RESOLVE_TURN_START_EFFECT；不根据这个旧动作名限制其只能在START调用。
- 满包时保留奖励和查看／合法整理窗口；强制待办不可放弃。
- 当前奖励未处理完，普通行动和END_TURN受阻；END产生奖励也要处理完才交给下个玩家。
- 少抽提醒DECK_INSUFFICIENT是成功结果，不退原费用，不自动重复抽。

## 8. 重试和恢复规则

网络不确定时，actions/roll/reroll原ID、原路径、原请求体重试。刷新后发起新的业务操作才用新ID及新版本。不要修改旧ID的stateVersion或dice。幂等重放可能是旧版本，不能覆盖更高版本UI。

版本过期、CONTEXT_CHANGED、CHECK_AUTHORIZATION_EXPIRED等先刷新player-view／pending-check。REQUEST_IN_PROGRESS原样稍后重试；REQUEST_ID_CONFLICT先核对首次操作。明确未知错误显示msg并保留上下文，不按中文错误文本做状态机。

重连／重启先active-session，然后定位自身playerId、建连，再恢复队首和判定。旧物理骰点未上传时后端没有记录，不假称可从服务端恢复该中间点数。不要清局或重建房间来“修复”离线暂停。
